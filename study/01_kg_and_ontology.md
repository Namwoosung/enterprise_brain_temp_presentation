# 1장. 지식 그래프와 온톨로지 — 무엇을 만드는가

**이 장의 목표**: "온톨로지", "KG", "RDF · OWL · 속성 그래프 · YAML"을 섞어 쓰지 않고 구분할 수 있다. 도메인 전문가가 아니어도 온톨로지를 시작하는 방법을 안다.
관련 질문: Q001 · Q002 · Q010 · Q012 · Q025 · Q026 · 상세 비교는 [ontology_formats.md](ontology_formats.md)

## 1.1 온톨로지(틀)와 데이터(내용) — TBox / ABox
- 지식을 두 종류의 문장으로 나눠 보는 표준 용어가 있다(기술 논리 · OWL의 바탕).
  - **TBox**(용어 상자): 개념과 관계의 정의. "정비 작업은 설비에서 수행된다", "설비는 FAB과 코드로 구분된다".
  - **ABox**(사실 상자): 개별 사실. "WO-1042는 FAB-A의 EQ-017에서 수행됐다".
- **KG = 데이터(ABox) + 그것을 조직하는 틀(TBox)** 으로 보는 것이 주류 정의다(Paulheim 2017, Hogan et al. 2021, Neo4j 진영의 "organizing principle"). "KG는 ABox만"이라는 말은 표준 정의가 아니라, 구현에서 틀을 따로 관리할 때 생기는 말버릇에 가깝다.
- 덱의 비유: 온톨로지 = 틀, KG = 그 틀에 채운 내용(2장).

## 1.2 넷은 같은 층이 아니다 — RDF · OWL · 속성 그래프 · YAML
| 이름 | 무엇의 이름 | 한 줄 |
|---|---|---|
| RDF | 데이터 모델 | 모든 것을 주어 – 술어 – 목적어(트리플)로 |
| 속성 그래프 | 데이터 모델 | 노드 · 관계에 라벨과 속성(Neo4j 등) |
| RDFS · OWL | 온톨로지 언어 | RDF 위에서 개념 · 관계의 의미를 논리로 정의 |
| YAML | 파일 문법 | 무엇을 적을지는 정해져 있지 않음 |
| SKOS · SHACL | 용어 체계 · 검증 규칙 | 동의어 · 상위어 / "이 속성은 꼭 1개" 같은 검사 |

- RDF는 시맨틱 웹(2001)을 위해 나왔다. RDF만으로는 추론이 거의 안 되고, **RDFS(클래스 계층, domain/range)** 부터 간단한 추론, **OWL** 은 동치 · 서로소 · 개수 · 역관계 · 이행 관계 같은 강한 논리를 더한다. 이 정의들도 결국 트리플로 적힌다.
- "의미를 이해한다"는 사람처럼 이해한다는 뜻이 아니라, **정해진 규칙으로 새 사실을 끌어내고 모순을 찾는다**는 뜻이다. 계산은 추론기가 한다.
- RDF 트리플에는 속성을 바로 붙일 수 없다. 출처 · 기간을 달려면 사실을 노드로 빼거나(reification) RDF-star를 쓴다. 속성 그래프는 관계 속성으로 바로 된다.
- OWL은 "개방 세계"라 "값이 없음"을 오류로 보지 않는다(모를 뿐). 없으면 오류로 잡는 건 SHACL이나 코드의 몫이다.

**같은 사실을 두 모델로**
```cypher
// 속성 그래프 (Cypher)
(:MaintenanceWork {wo_id:'WO-1042'})-[:ON_EQUIPMENT {source:'CMMS'}]->(:Equipment {fab:'FAB-A', code:'EQ-017'})
```
```turtle
# RDF (Turtle) — 관계 출처는 따로 노드나 RDF-star가 필요
:WO-1042 a :MaintenanceWork ; :onEquipment :FAB-A_EQ-017 .
```

## 1.3 덱은 어떻게 나눴나
| 층 | 덱의 선택 | 담는 것 |
|---|---|---|
| 정의 (TBox, 기준) | YAML + Git (자체 형식) | 클래스 · 키 · 필수값 · 허용값 · 관계 방향 · 기준 시스템 · 예시 · 검토 기준 |
| 생성물 | JSON Schema · 검증 코드 · DB 제약 · (선택) SHACL | 정의에서 기계적으로 만든 검사 장치 |
| 데이터 (ABox) | 속성 그래프 (데모는 Neo4j) | 개체 · 관계 · 근거 ID · 유효 기간 |
| 원본 · 원장 | 파일 · Parquet · (나중에) RDB | 원문 · 수집 기록 · 검토 이력 |
| 교환 (선택) | RDF / OWL 내보내기 | 외부 표준 어휘와 연결할 때 |

- 일반적인 KG 구축 방식은 하나로 정해져 있지 않다. A 시맨틱 웹(OWL + RDF) · B 속성 그래프 · C 혼합(정의는 별도 파일, 데이터는 속성 그래프) · D 가상 KG(원천 DB 그대로 + 매핑) · E LLM 추출(GraphRAG)이 주로 쓰인다. **덱은 C를 기본으로 D · E를 섞는다.**

## 1.4 agent용이면 OWL이 꼭 필요한가
- 아니다. agent에게 필요한 건 ① 흔들리지 않는 개념 · 관계 정의 ② 같은 대상을 같은 ID로 묶은 데이터 ③ 근거와 시점 ④ 도구로 질의할 수 있는 구조 ⑤ LLM이 읽을 수 있는 설명이다. YAML 정의 + 속성 그래프로 다 할 수 있고, LLM 도구들(Neo4j GraphRAG, LlamaIndex PropertyGraphIndex)도 이 조합을 기본으로 쓴다.
- RDF · OWL을 고려할 때: 외부 표준 어휘와 연결, 조직 간 데이터 교환, 클래스 계층 같은 규칙 추론을 DB가 해 주길 원할 때.
- KG가 다시 주목받은 직접 원인은 LLM의 환각 · 근거 부족을 보완하려는 수요다(2012 Google Knowledge Graph로 "KG"라는 말이 대중화, 2023년 이후 GraphRAG로 재부상).

## 1.5 도메인 전문가가 아니어도 온톨로지를 시작하는 법
- **처음부터 전 범위를 덮지 않는다.** 업무 질문(Competency Question, CQ)으로 범위를 정하고 반복해서 넓히는 것이 표준 방법론이다(Grüninger & Fox, Ontology Development 101, NeOn).
- 역할 분담: **개발자는 모델링, 전문가는 판정.** 전문가에게 "온톨로지를 만들어 달라"가 아니라 "EQ-017은 FAB마다 따로 있나요?" 같은 예/아니오 질문을 묻는다.
- 순서:
  1. CQ 5~10개 모으기 (예: "FAB-A EQ-017의 최근 PT-V42 교체 이력은?")
  2. CQ의 명사 → 클래스 후보, 동사 → 관계 후보. 그 이상은 만들지 않음
  3. 기존 자산 재사용: DB 스키마 · 코드표 · 업계 표준(제조 ISA-95, 설비 상태 SEMI E10)
  4. 작은 데이터로 넣어 보고 CQ가 답하는지 테스트
  5. 정의 밖 개념은 확장 후보 큐로 → 빈도순 전문가 리뷰 → 버전 올림
- 정의 파일의 수준: CQ에 답하는 데 필요한 만큼. 블록은 ① 클래스 ② 관계 ③ 추출 예시 ④ 검토 기준 ⑤ 정의 밖 처리(17a장). 같은 생각의 공개 도구로 **LinkML**(YAML → JSON Schema · Pydantic · SHACL · OWL · SQL 생성)이 있다.

### 확인 질문
1. "WO-1042는 EQ-017에서 수행됐다"는 TBox인가 ABox인가?
2. RDF와 OWL의 관계를 한 문장으로 말하면?
3. 관계에 "출처"를 붙이기가 RDF보다 속성 그래프에서 쉬운 이유는?
4. 처음 온톨로지 범위를 정할 때 무엇부터 모으나?

<details><summary>답</summary>

1. ABox(개별 사실). 2. RDF는 데이터를 적는 모양(트리플), OWL은 그 RDF로 적는 개념 정의용 어휘 + 논리. 3. 속성 그래프는 관계에 키-값 속성을 바로 달 수 있고, RDF 트리플은 그 자체에 속성을 못 단다. 4. 업무 질문(CQ).
</details>
