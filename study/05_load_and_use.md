# 5장. 적재와 활용 — 그래프에 무엇을 두고, 어떻게 쓰이게 하나

**이 장의 목표**: 그래프에 무엇을 넣고 무엇을 밖에 둘지, 근거 · 시간 · 계보를 어떻게 남길지, agent가 KG를 어떻게 쓰게 할지 안다.
관련 질문: Q014 · Q016 · Q018 · Q030 · Q032 · Q035 · Q036

---

## 5.1 방법론이 먼저, DB는 구현 예
- 발표에서 다루는 문제(ER, 근거 · 시점, 검증, 사람 검토, 버전)는 대부분 **DB 바깥 파이프라인**의 일이다. 그래프 DB는 "승인된 사실의 조회용 사본"이라 Neo4j든 다른 그래프 DB든 방법은 같다.
- Neo4j가 실제로 영향을 주는 곳은 좁다: 제약 기능 범위(에디션별), 플러그인, 데이터 브랜치 부재, Cypher 문법(MERGE 함정). 데모는 시각화가 좋아서 Neo4j를 썼다.

## 5.2 저장 방식 비교와 우리 선택 (23a장)
| 저장 방식 | 장점 | 단점 | 맞는 경우 |
|---|---|---|---|
| 속성 그래프 DB | 관계 탐색 · 개발 편함 | 표준 의미 · 추론 약함 | agent · 사람의 탐색 조회 |
| RDF 트리플 저장소 | 표준 · 추론 · 외부 연계 | 배우기 어려움 | 표준 어휘 연계 · 조직 간 교환 |
| RDB 노드 · 엣지 테이블 | 운영 익숙 · 트랜잭션 | 다단계 탐색 쿼리 복잡 | 원장 · 검토 이력 |
| 가상 KG (원천 + 매핑) | 복사 없음 · 항상 최신 | 문서에 약함 | 대량 측정값 · 이력 |

**우리 선택**: 조회 사본은 속성 그래프, 대량 값은 원천에 두고 참조, 적재는 증분 MERGE + 가끔 전체 재구축으로 차이 확인.

## 5.3 실제 데이터와 잇기 — 그래프엔 뼈대, 값은 원천 (Q018)
- 그래프에 세부 데이터를 다 넣지 않는다. **개체와 관계(뼈대)** 를 두고, 대량 값은 원천에 둔 채 **어디서 어떻게 가져오는지**를 연결한다.
- 데이터 종류별:
  - **RDB(MES · CMMS)**: 설비 · 부품 · 작업 같은 마스터와 관계만 그래프로. 측정값 · 이력은 RDB에 두고, 개념 ↔ 테이블 · 컬럼 매핑으로 필요할 때 SQL. 표준 이름은 OBDA(가상 KG), 매핑 표준 R2RML, 구현 Ontop. NVIDIA Auto Ontology도 같은 계열.
  - **엑셀 2만 개**: 파일마다 `Dataset` 노드(경로 · 담당자 · 시트/열 스키마 · 대상 설비 · 기간)를 만들어 개체와 연결(데이터 카탈로그). 값은 Parquet + DuckDB로 조회, 그래프엔 요약 · 핵심 사실만.
  - **문서**: Document → Chunk(텍스트 · 벡터) → 언급된 개체. 그래프엔 검증된 사실만.
- 참조 예:
```cypher
(:Equipment {fab:'FAB-A', code:'EQ-017'})-[:HAS_DATA]->
  (:Dataset {system:'MES', table:'eqp_state_hist', key:'EQ-017', query:'SELECT ... WHERE eqp_id=$code'})
```
- agent 흐름: ① 그래프로 어느 설비 · 작업인지 찾고 ② 연결된 Dataset의 조회 방법으로 값을 가져오고 ③ 문서 조각으로 근거를 붙인다.

## 5.4 근거는 남기되, 그래프는 가볍게 (Q016)
- 근거(provenance)를 남기는 건 필요하다(W3C PROV-O): 원본이 정정 · 삭제되면 그 문서의 사실을 찾아 무효화, 출처 충돌 판단, 답변 인용, 권한 필터, "검증됨"도 확률적이라 되짚을 길.
- 하지만 내용을 그래프에 다 넣을 필요는 없다. 흔한 절충(23장 C안):
  - 그래프: 근거 ID 목록 · 확실성 · 유효 기간
  - 원장: 원문 위치 · 인용문 · 추출 모델 · 프롬프트 버전 · 검토 기록
  - agent 조회 뷰는 근거 노드를 빼고, 필요할 때 ID로 원장을 찾아간다.

## 5.5 시간 축 두 개 — 언제 사실이었나 / 언제 알았나 (Q030)
- **유효 시간**: 현실에서 참이었던 기간. **기록 시간**: 시스템이 알게 되거나 고친 때. 둘을 따로 두는 것이 bi-temporal 모델.
- 덮어쓰면 "3월 5일에 우리가 알던 기준"을 다시 볼 수 없고 agent가 옛 정보를 최신으로 답한다(6장 사례).
- 관계에 `valid_from / valid_to` + `recorded_at / invalidated_at`. 충돌하면 지우지 않고 기존 사실의 `valid_to`를 닫는다. Graphiti(Zep)가 LLM KG에 이 방식을 넣은 예. 바뀌는 사실(상태 · 기준값)부터 적용.

## 5.6 계보 — 어느 실행 · 어느 버전에서 왔나 (Q032)
- 근거 ID는 "어느 문서", 계보는 "어느 파이프라인 실행 · 어느 프롬프트 · 규칙 버전". 잘못된 사실을 찾으면 같은 실행의 다른 사실도 한꺼번에 찾을 수 있다.
- 처음엔 실행 기록(run id · 입력 해시 · 온톨로지 · 프롬프트 · 모델 버전)으로 충분(데모 `runs/`, 26장). Airflow를 쓰면 OpenLineage 연동으로 자동 수집.

## 5.7 agent가 KG를 쓰게 하려면
- **MCP로 도구 내보내기(Q035)**: KG 쪽에서 "설비 이력 조회", "근거 원문 보기", "질문 큐에 올리기" 같은 도구를 한 번 정의하면 여러 agent가 쓴다. 읽기 전용 · 정해진 질의(CQ)부터. 도구 설명문이 곧 프롬프트이니 정의 YAML의 설명을 가져다 쓴다.
- **그래프 + 벡터 혼합 검색(Q036)**: 질문 → 벡터로 관련 조각 → 언급된 개체 → 1~2단계 이웃 사실 → 근거와 함께 답. 구축 쪽에서 조각 ↔ 개체 연결(MENTIONS), 근거 ID, 유효 기간을 남겨 둬야 가능하다. **구축 설계가 검색 품질을 정한다.** (상세는 발표 3 · 4)
