# NVIDIA Auto Ontology는 온톨로지를 어떻게 만드나

조사일 2026-11-24. 관련 질문: [qna_notes.md](../qna_notes.md) Q019. 발표 29장(최신 도구)과 28장(방법론)의 배경 자료입니다.

> 출처 구분: **[공식]** = GitHub 저장소 README · `docs/architecture.md` · 운영 스킬 문서, **[분석]** = 제3자 블로그(icorer.com, 2026-11)의 코드 분석. 둘이 다른 부분은 따로 표시했습니다. 프로젝트가 공개된 지 몇 주 안 된 상태라 세부는 빠르게 바뀔 수 있습니다.

## 1. 한 줄 요약
**RDB 메타데이터에서 시맨틱 레이어(용어 · 컬럼 매핑 · 관계 · 지표) 초안을 만들고(Generate), 사람이 실제 질문으로 시험하고 고쳐서 인증하고(Certify), agent가 그걸로 SQL을 만들어 답하는(Answer) 오픈소스 Python 프레임워크.** Apache 2.0 [공식].

- "DB를 분석해 온톨로지를 자동으로 만든다"는 이해는 맞습니다. 단, 결과물은 OWL 같은 형식 온톨로지가 아니라 **text-to-SQL용 시맨틱 레이어**에 가깝습니다.
- 공개 문서 기준으로 회의록 · 메일 같은 비정형 문서는 입력에 없습니다.

## 2. 입력
| 입력 | 필수 여부 | 쓰임 |
|---|---|---|
| 테이블 · 컬럼 · 뷰 · 기본키 · 선언된 외래키 | 필수 | 뼈대 |
| 쿼리 이력(예: Snowflake QUERY_HISTORY) | 엔진이 제공하면 | 자주 쓰는 계산식 → 지표(SQL 속성) 제안 |
| 표본 행(테이블당 최대 1,000행), 저카디널리티 컬럼의 고유값 | 설정 | 고유 컬럼 판정, 값 설명 |
| 저장된 분석 SQL, 기존 시맨틱 모델(Ossie YAML), 용어집 · 프롬프트 | 선택 | 초안 품질 보강 |

지원 DB(README): PostgreSQL, MySQL, Databricks, Snowflake, ClickHouse, Trino, Apache Kyuubi, HeavyDB, DuckDB, SQLite [공식].

## 3. 만드는 과정 (Semantic compilation)
설정에서 켜면 시작 시 · 24시간마다 · 요청 시 실행됩니다 [공식].

**① 카탈로그 수집**
- SQL로 테이블 · 컬럼 · 키 · 뷰 · 쿼리 이력을 읽음
- (선택) 개인정보 컬럼 탐지: 규칙 먼저, 애매한 것만 LLM
- 테이블 · 컬럼을 임베딩해 pgvector에 색인

**② 테이블별 처리** (세 테이블씩)
| 하는 일 | 방식 |
|---|---|
| 표본에서 값의 95% 이상이 고유하면 고유 컬럼으로 표시 | 규칙(SQL) |
| 날짜 형식 추론 | 규칙 |
| 외래키 · 연결(junction) 테이블 후보 찾기, 선언된 키와 합침 | LLM |
| 컬럼 설명 작성 | LLM |
| **용어(term)** 이름 · 설명 · 동의어 · 표시 이름 작성 | LLM |
| 용어 임베딩 | 임베딩 모델 |

**③ 테이블 간 처리**
| 하는 일 | 방식 |
|---|---|
| 같은 스키마 사본(OLD_ROOMS / NEW_ROOMS)을 "용어 가족"으로 묶음 | 규칙 |
| 외래키 컬럼을 어느 용어에 연결할지: 선언된 키 우선, 없으면 임베딩 검색 + LLM 선택 | 임베딩 + LLM |
| **추론한 연결은 두 컬럼을 실제로 조인해 행이 나올 때만 저장** | 규칙(데이터 검증) |
| 여러 연결 후보 중 기본 조인 선택 | LLM |
| 쿼리 이력의 SQL 식에서 "SQL 속성(지표)" 제안(용어당 최대 10개) | LLM |
| 다리 테이블용 SQL 속성 작성, 소유 용어 선택 | LLM + 재정렬 모델 |

- 관계를 어떻게 추론하는지는 공식 문서와 분석 글이 다릅니다. 공식 문서는 "선언된 키 → 임베딩 + LLM 제안 → 조인으로 확인"이고, 분석 글은 "`_id` 접미사 · 타입 · 설명 · 표본 고유성" 같은 휴리스틱을 듭니다. 분석 글은 이전 커밋을 본 것이라 차이가 있을 수 있습니다.
- 모델은 네 역할(추론용, 비추론용, 임베딩, 재정렬)로 나뉘고 기본값은 NVIDIA Nemotron 계열입니다. OpenAI 호환 자체 엔드포인트도 쓸 수 있습니다 [공식].

## 4. 결과물의 모양
- 저장: PostgreSQL 17 + pgvector [공식].
- 요소 [공식]:
  - **용어(term)**: 업무 개념. 설명 · 동의어 · 표시 이름
  - **컬럼 속성**: 용어 ↔ 테이블 · 컬럼 매핑
  - **SQL 속성**: 용어에 붙은 이름 있는 계산식(지표 정의)
  - **의미적 외래키**: 용어 사이 관계 + 기본 조인
  - 용어 가족, 저장된 분석, 인증 상태
- README는 이걸 여섯 질문으로 설명합니다: 개념(Concept) · 매핑(Mapping) · 관계(Relationship) · 지표(Metric) · 계보(Lineage) · 인증(Certification).
- 필드 단위 스키마는 OpenAPI 명세와 DB 마이그레이션 파일에 있고, 이번 조사에서는 보지 않았습니다.

## 5. 인증(Certify)은 무엇을 하나
- 사람이 실제 질문으로 초안을 시험해 보고(채팅 또는 MCP의 `check_answerable` · `ask_question`), 용어 · 설명 · SQL 속성 · 관계를 고친 뒤 인증합니다. 고친 것은 다음 컴파일에도 유지됩니다(조인 선택은 매번 다시 고름) [공식].
- **인증은 게이트가 아닙니다.** 공식 문서가 "인증은 UI와 검색 결과에 검토됨을 표시할 뿐 agent의 조회 방식은 바꾸지 않는다"고 적고 있습니다 [공식]. 분석 글도 조회 코드에서 인증 플래그를 쓰는 곳을 찾지 못했다고 합니다 [분석].
- 시사점: "사람 인증 단계를 제품에 넣었다"는 것과 "인증하지 않은 것은 쓰이지 않는다"는 다릅니다. 우리 설계에서는 승인 전 사실이 조회에 나오지 않도록(또는 "미검토"로 표시되도록) 막는 장치를 따로 만들어야 합니다.

## 6. 답하는 방식
- 추론 모델이 도구를 하나씩 고르는 ReAct 루프입니다. `retrieve`(용어 · 속성 · SQL 속성 · 분석을 벡터 + 이름으로 검색, 조인 경로 반환) → `run_sql`(카탈로그 이름 검사 후 실행, 최대 100행) → `submit`(최종 SQL과 답) [공식].
- 기본 한도: 도구 호출 24번, SQL 실행 10번. 되묻기(clarifying question)는 하지 않습니다 [공식].
- `check_answerable`: 질문의 개체를 뽑아 시맨틱 레이어에 대응 항목이 있는 비율을 계산합니다. 이 계산 자체는 산술입니다 [공식][분석].
- MCP 서버로 읽기 전용 도구 9개를 내보냅니다 [공식].

## 7. 한계 · 주의
- 비정형 문서(회의록, 메일, 매뉴얼)는 다루지 않습니다.
- 컴파일은 아직 용어가 없는 테이블만 새로 처리합니다. 기존 테이블에 컬럼이 늘었을 때의 처리는 문서에 없습니다(분석 글도 열린 질문으로 둠).
- 기본 설정의 NIM 엔드포인트는 데이터를 NVIDIA 호스팅 모델로 보냅니다. 사내 데이터라면 자체 엔드포인트를 써야 합니다 [공식].
- 내부 포트(3001, 3002)는 인증이 없으므로 외부에 노출하면 안 됩니다 [공식].
- 사용 빈도 순위 기능은 아직 동작하지 않습니다("가장 많이 쓰인 10개"가 아니라 "처음 찾은 10개") [공식][분석].
- 벤치마크 성능 주장(README)과 "공개된 정확도 수치가 없다"는 분석 글의 지적이 엇갈립니다. 도입 전 직접 평가가 필요합니다.

## 8. 우리 구축에 가져올 힌트
| Auto Ontology가 하는 것 | 우리에게 주는 힌트 | 발표 연결 |
|---|---|---|
| 스키마 + 표본 + 쿼리 이력으로 초안 생성 | MES · CMMS의 스키마와 실제 쿼리에서 온톨로지 초안을 뽑을 수 있다. 개발자가 도메인을 몰라도 시작점이 생김 | 28장 "기존 DB에서 끌어내기" |
| LLM이 관계를 제안하고 **실제 조인으로 확인** | LLM 제안은 데이터로 검증한다. 우리 검증 단계의 원천 대조와 같은 원리 | 21장 |
| 규칙 단계와 LLM 단계를 명확히 분리 | 결정적으로 할 수 있는 건 규칙, 이름 붙이기 · 설명 · 후보 제안만 LLM | 10장 |
| 지표(SQL 속성)를 용어에 붙여 관리 | 엑셀 · 보고서의 계산 규칙도 정의 파일에 넣을 대상 | 17a장 |
| 사람이 실제 질문으로 시험 후 인증 | CQ로 시험하는 흐름과 같음. 단, 인증이 실제로 막는지는 우리가 설계 | 24장 · 22장 |
| 정형 DB 전용 | 문서 쪽(추출 · 검증 · 근거)은 우리 파이프라인이 따로 필요 | 17~22장 |
| 그래프 개념을 Postgres 테이블에 저장 | 정의 · 원장 · 벡터를 한 DB에 두는 선택도 가능. 그래프 DB는 조회 사본 | 23장 |

**정리:** "DB에서 초안 → 데이터로 검증 → 사람이 질문으로 시험 → 인증"이라는 흐름은 그대로 참고할 만합니다. 다만 결과물이 형식 온톨로지가 아니라 text-to-SQL용 매핑이라는 점, 문서를 다루지 않는다는 점, 인증이 게이트가 아니라는 점은 우리 설계에서 보완할 부분입니다.
